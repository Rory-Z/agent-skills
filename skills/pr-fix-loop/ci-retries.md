# CI retries

This procedure belongs only to `pr-fix-loop`; it overrides the immediate infrastructure-blocker path inherited from `emqx-pr`.

## Budget and waiting

Allow at most three additional CI rerun requests in one Fix Session, shared across workflows and heads. The original runs do not count. A new invocation starts at zero; do not reconstruct counts from GitHub history. Keep the count through Fix Cycles within this invocation. CI retries create no commits, Fix Cycle trailers, or Recovery Epochs.

Wait five minutes after establishing a qualifying failure before each rerun. While waiting or while CI runs, keep the agent turn open and report progress. Poll at intervals of at most 60 seconds instead of using an uninterrupted `gh pr checks --watch`; resume any live terminal session until it exits. A pending check is not a failed attempt.

## Procedure

1. On every poll, confirm the PR is open and its head still equals the local pushed `HEAD`, then run `scripts/resolve-recovery-state.sh` with the existing repository, PR, and Trusted Reviewer arguments. If the head changed, stop with the race details. If there is a current Effective Review Result, leave already-running CI intact and return to **Wait for feedback** to process it through the existing gates. `pass`, `review-blocked`, `recovery-required`, and `closed` follow their existing stop paths. Only `waiting` continues CI handling. Treat resolver errors as read failures, never as evidence that no Review Result exists; stop after three consecutive read failures, and immediately on explicit permission or authentication failure.
2. Read `gh pr checks <pr-number> --repo <owner/repo>` and the relevant workflow run. Pending checks continue polling. For failed checks, inspect the latest attempt's logs, for example with `gh run view <run-id> --repo <owner/repo> --log-failed`. Establish a transient infrastructure cause such as registry image-pull EOF or network timeout. An unrelated failure alone is insufficient. Authentication, permissions, unknown causes, and code/test defects do not qualify; return to the Fix Cycle's existing check-repair or blocker path. Missing or unreadable checks cannot establish success.
3. Identify the failed GitHub Actions job and verify its run belongs to this repository and the exact current PR head. Use `gh run view <run-id> --repo <owner/repo> --json headSha,status,attempt,jobs` for the run and job database IDs. Retry only ordinary CI validation within the existing authorization; deployment or Production jobs and their dependencies remain outside this permission. If the run cannot be tied to the current head, or the required rerun is unavailable or out of scope, stop with that blocker.
4. If all three rerun requests have been used and a qualifying failure remains, stop. Otherwise wait the five-minute delay, continuing step 1 and checking CI status. Immediately before requesting a rerun, repeat the head, Review Result, and latest run-attempt checks. If another actor already reran the job, observe that attempt instead of duplicating it. Wait for the run to complete before requesting its rerun; if it has recovered, skip the rerun.
5. Increment the session count and use `gh run rerun <run-id> --repo <owner/repo> --job <job-database-id>` for the qualifying failed job and its dependencies. Use `--failed` instead only when every failed job qualifies, including a downstream gate whose sole failure is the qualifying upstream failure. Each command consumes one request from the shared budget. On an ambiguous request error, inspect the run before doing anything else; do not blindly issue duplicate requests. Stop on rejection or when acceptance cannot be established.
6. Observe the new attempt with steps 1–2; do not mistake the previous attempt's failure for the new result. Inspect fresh logs after each failure. If only a downstream gate remains failed after upstream recovery, verify its failure is solely caused by that upstream attempt before rerunning it within the same budget. After recovery, verify the exact head again and reread all PR checks. Only verified passing checks complete CI validation; then continue Fix Cycle step 8 and wait for the next Effective Review Result.

On a blocker, report the exact head, failed check and run link, relevant failure evidence, rerun requests used out of three, and the stopping reason. On a Pass Signal, report review success and the observed CI status separately, including pending, failed, or unverified checks. Never present review success as passing CI.
